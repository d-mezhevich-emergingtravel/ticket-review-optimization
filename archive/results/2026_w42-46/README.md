# Датасет 2026, недели 42–46

Из сырых Excel-выгрузок собирается `dataset_for_request.csv`: одна строка на тикет с полями `ticket_id`, `state_date`, `log`, `com`, `db_type`. Файл загружается в две sandbox-таблицы, global и ru, и к каждой применяется своя версия запроса. Две выгрузки запросов склеиваются в финальный датасет `result/dataset.xlsx`, при этом ограничиваются сильные выбросы в суммах.

Структура папки:

| Папка | Что внутри |
|---|---|
| `raw/` | сырые выгрузки одного формата, прямо в папке, без подпапок. Все категории приходят одной выгрузкой, поэтому `main.xlsx` в этом периоде не собирается |
| `scripts/` | `check_fields.py`, `prepare_dataset.py`, `merge_results.py`, `outliers.py` |
| `queries/global/`, `queries/ru/` | `rvi_1w.sql`, `rvi_3w.sql`, `rvi_5w.sql` для каждого контура |
| `result/` | `dataset.xlsx` (финальный датасет, собирает скрипт) |
| `result/temp/` | `dataset_for_request.csv` (собирает скрипт), `res_req_global.xlsx` и `res_req_ru.xlsx` (выгрузки запросов) |

## Порядок работы

Период: `state_date` с 12.10.2026 по 12.11.2026. Взяты недели 42–46, а не 41–45: сотрудник сообщил, что 41-я неделя 2026 года у него невалидная. 46-я неделя неполная, с понедельника по четверг: сотрудник проверил её только по 12.11.2026, выгрузок за 13–15.11 нет.

1. Положить Excel-файлы прямо в `raw/`, один файл на день (например, `2026-11-11.xlsx`). Подпапки не читаются, временные файлы `~$…` пропускаются. Данные читаются с листа `Result`. Если файлов нет, скрипты останавливаются.

2. Проверить поля (необязательно, `prepare_dataset.py` делает ту же проверку):

   ```
   python3 scripts/check_fields.py
   ```

3. Собрать датасет для запроса:

   ```
   python3 scripts/prepare_dataset.py
   ```

   Если какой-то файл не прошёл проверку или в `ticket_link` попался неизвестный домен, скрипт пишет, что не так, и останавливается, не трогая старый `result/temp/dataset_for_request.csv`.

4. Загрузить `result/temp/dataset_for_request.csv` в sandbox-таблицы обоих контуров: `analytics_sandbox` для global и `ru_analytics_sandbox` для ru. Подставить имена таблиц вместо `__` в выбранную версию запроса в `queries/global/` и `queries/ru/`. Версия окна должна быть одна и та же в обоих контурах.

5. Выполнить запросы и выгрузить результаты в `result/temp/res_req_global.xlsx` и `result/temp/res_req_ru.xlsx`.

6. Собрать финальный датасет:

   ```
   python3 scripts/merge_results.py
   ```

Команды написаны для запуска из этой папки (`2026_w42-46/`). Пути строятся от папки периода, поэтому скрипты можно запускать из любой директории, указав полный путь к скрипту.

## Команды

| Задача | Команда |
|---|---|
| Проверить поля сырых выгрузок | `python3 scripts/check_fields.py` |
| Собрать датасет для запроса | `python3 scripts/prepare_dataset.py` |
| Собрать финальный датасет из выгрузок запросов | `python3 scripts/merge_results.py` |
| Проверить или собрать из другой папки с сырыми данными | добавить путь аргументом: `python3 scripts/prepare_dataset.py "путь/к/папке"` |

## Скрипты

### `scripts/check_fields.py`

На листе `Result` каждого файла проверяет:

- `ticket_id`, `state_date`, `ticket_link`: колонки есть и заполнены во всех строках (строка из пробелов считается пустой). Вместо `state_date` подходит `resolve_date`: в дневных выгрузках дата тикета лежит в нём;
- `log` и `com`: колонки есть, пустые значения допустимы. Вместо `com` подходит `comm`;
- `dop_check`: колонки может не быть. Если она есть, допустимы только пустые значения и `true`, иначе файл не проходит проверку.

Перед проверкой лист читается функцией `read_result`:

- в части выгрузок `ticket_link` записан формулой `=HYPERLINK("url", …)` без сохранённого результата. Excel показывает ссылку, а pandas видит пустую ячейку. Тогда URL берётся из текста формулы. Если строки листа не удаётся сопоставить один в один, скрипт останавливается;
- полностью пустые строки (заполнена только дата) отбрасываются.

Выводит результат по каждому файлу. Код выхода 1, если хоть один файл не прошёл.

### `scripts/prepare_dataset.py`

1. **Проверка** той же функцией, что в `check_fields.py`. Если хоть один файл не прошёл, сборка не запускается.
2. **Сборка.** Строки с `dop_check = true` отбрасываются, скрипт печатает, сколько строк убрано в каждом файле. Остальные строки не фильтруются. Со всех файлов берутся `ticket_id`, `state_date`, `log`, `com` (`resolve_date` переименовывается в `state_date`, `comm` в `com`). По `ticket_link` добавляется `db_type`:

   | Ссылка начинается с | `db_type` |
   |---|---|
   | `https://crm.ostrovok.in/` | `ru` |
   | `https://crm.etg.team/` | `global` |

   Ссылка с другим доменом останавливает сборку.
3. **Дубли `ticket_id`.** Остаётся строка с заполненным `log`. Если `log` заполнен у всех или ни у кого, остаётся строка с более ранним `state_date`.

Скрипт печатает минимальный и максимальный `state_date`: максимальный должен быть не позже 12.11.2026.

Результат: `result/temp/dataset_for_request.csv`, CSV с разделителем `;`, кодировка UTF-8, первая строка — заголовки, `state_date` в формате `YYYY-MM-DD`.

### `scripts/merge_results.py`

1. Читает лист `Result` из `result/temp/res_req_global.xlsx` и `result/temp/res_req_ru.xlsx`. Колонки должны совпадать с колонками финального датасета, включая порядок, иначе скрипт останавливается.
2. Склеивает строки и проверяет дубли `ticket_id`: печатает, сколько их, в каких файлах и примеры. Дубли не исправляются.
3. Ограничивает выбросы (`outliers.py`) и сохраняет `result/dataset.xlsx` (лист `Result`). Файл перезаписывается при каждом запуске.

### `scripts/outliers.py`

Правило ограничения сильных выбросов, используется в `merge_results.py`. Для `gross`, `mail_sum` и `dispute_sum` значения тикетов с событием (не `null` и больше 0) сортируются по убыванию и режутся на бакеты везде, где значение больше следующего в 2 раза и больше (константа `GAP`). Основная масса — бакет с наибольшим числом тикетов, при равенстве нижний. Граница — верхнее значение основной массы. Все значения в бакетах выше неё считаются выбросами и заменяются границей. Если основная масса — самый верхний бакет, сумма не меняется. Правило принято 20.11.2026 вместо прежнего, которое искало разрывы только подряд с самого верха и пропускало выбросы ниже первого непрерывного разрыва.

- `net` ограничивается по модулю с сохранением знака по выбросам `gross`, `gross = abs(net)`;
- `mail_sum` и `dispute_sum` ограничиваются каждая по своим выбросам;
- флаги, нули и `null` не меняются, поэтому ER и медианы остаются прежними.

Скрипт печатает верх каждого распределения с границей и множителем к следующему значению, чтобы было видно, что обрезано.

## Запросы

Логика запросов одна и та же, версии отличаются только контуром и окном.

Все действия считаются для сотрудника `5863`. Окно тикета: от понедельника недели `state_date` до `window_end` включительно:

| Файл | `window_end` | Дней в окне |
|---|---|---|
| `rvi_1w.sql` | `window_start + 13` | 14 |
| `rvi_3w.sql` | `window_start + 27` | 28 |
| `rvi_5w.sql` | `window_start + 41` | 42 |

Внутри контура версии отличаются только `window_end`. Контуры отличаются фильтром и схемами:

| | global | ru |
|---|---|---|
| sandbox-таблица | `analytics_sandbox.__` | `ru_analytics_sandbox.__` |
| фильтр в `input_data` | `sb.db_type = 'global'` | `sb.db_type = 'ru'` |
| CRM | `crm.*` | `ru_crm.*` |
| booking | `public.booking` | `ru_public.booking` |
| курс USD | `analytics.currency_converter` | `ru_analytics.currency_converter` |

Логику правь в `queries/global/rvi_1w.sql`. Остальные версии global пересобирай из него заменой числа в `window_end`, ru-версии — заменой фильтра и схем по таблице выше.
