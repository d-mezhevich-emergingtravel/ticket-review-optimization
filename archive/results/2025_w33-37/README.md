# Датасет 2025

Из сырых Excel-выгрузок за 2025 год собираются два датасета для запроса: `dataset_for_request.csv` из всех категорий и `dataset_for_request_main.csv` только из `main/`. В каждом одна строка на тикет с полями `ticket_id`, `state_date`, `log`, `com`. Каждый файл загружается в sandbox-таблицу, к нему применяется один из запросов из `queries/`. Из выгрузок запросов скрипт собирает два финальных датасета периода, `result/dataset.xlsx` и `result/main.xlsx`, ограничив сильные выбросы в суммах.

Структура папки:

| Папка | Что внутри |
|---|---|
| `raw/` | сырые выгрузки по категориям |
| `scripts/` | `prepare_dataset.py`, `finalize_dataset.py`, `outliers.py` |
| `queries/` | `rvi_1w.sql`, `rvi_3w.sql`, `rvi_5w.sql` |
| `result/` | `dataset.xlsx` и `main.xlsx` (финальные датасеты, собирает скрипт) |
| `result/temp/datasets_for_request/` | `dataset_for_request.csv` и `dataset_for_request_main.csv` (собирает скрипт) |
| `result/temp/request_results/` | `request.xlsx` и `request_main.xlsx` (выгрузки запросов) |

## Порядок работы

1. Разложить Excel-файлы по папкам категорий внутри `raw/`:

   | Папка | Что кладём | Пример имени |
   |---|---|---|
   | `main/` | недельные выгрузки ошибок | `week33_mistakes.xlsx` |
   | `closed/` | недельные выгрузки закрытых тикетов | `closed_week33.xlsx` |
   | `zero_losses/` | недельные выгрузки тикетов без убытка | `Tickets_with_33_losses.xlsx` |

   Данные читаются с листа `Result`. Во всех файлах уже должны быть заполнены `ticket_id` и `state_date`.

2. Собрать датасеты для запроса:

   ```
   python3 scripts/prepare_dataset.py
   ```

   Если на шаге проверки какой-то файл не прошёл, скрипт пишет, что не так, и останавливается, не трогая старые датасеты в `result/temp/datasets_for_request/`. Нужно поправить файл и запустить заново.

3. Каждый датасет из `result/temp/datasets_for_request/` загрузить в свою sandbox-таблицу, подставить её имя в выбранную версию запроса, выполнить запрос и выгрузить результат в `result/temp/request_results/`. Версия окна должна быть одна и та же для обоих датасетов.

   | Датасет для запроса | Выгрузка запроса |
   |---|---|
   | `dataset_for_request.csv` | `request.xlsx` |
   | `dataset_for_request_main.csv` | `request_main.xlsx` |

4. Собрать финальные датасеты:

   ```
   python3 scripts/finalize_dataset.py
   ```

Команды ниже написаны для запуска из этой папки (`2025_w33-37/`). Скрипты находят данные сами, их можно запускать и из любой другой директории, указав полный путь к скрипту.

## Команды

| Задача | Команда |
|---|---|
| Собрать датасеты для запроса | `python3 scripts/prepare_dataset.py` |
| То же для другой папки с сырыми данными | добавить путь аргументом: `python3 scripts/prepare_dataset.py "путь/к/папке"` |
| Собрать финальные датасеты из выгрузок запросов | `python3 scripts/finalize_dataset.py` |

## Скрипты

### `scripts/prepare_dataset.py`

Два шага подряд:

1. **Проверка.** В каждом файле на листе `Result` есть заполненные `ticket_id` и `state_date`, есть колонки `log` и `com`. В Main и Closed ещё заполнен `min_weekly_change_counter`. Если хоть один файл не прошёл, сборка не запускается.
2. **Сборка.** Отбор строк по категориям:
   - Main, Closed: `min_weekly_change_counter = 1`;
   - zero_losses: все строки без фильтра.

   Если `ticket_id` повторяется, остаётся строка с заполненным `log`. Если `log` заполнен у всех или ни у кого, остаётся строка с более ранним `state_date`.

   Собираются два датасета с одинаковыми колонками:

   | Файл | Из каких строк |
   |---|---|
   | `dataset_for_request.csv` | все категории |
   | `dataset_for_request_main.csv` | только `main/` |

   Оба файла сохраняются в `result/temp/datasets_for_request/`, формат: CSV с разделителем `;`, кодировка UTF-8, первая строка — заголовки, `state_date` в формате `YYYY-MM-DD`.

   Дубли в каждом разбираются отдельно. Поэтому у тикета, который есть и в Main, и в другой категории, `state_date` и `log` в двух датасетах могут отличаться: в основной может попасть строка из другой категории.

### `scripts/finalize_dataset.py`

Собирает два финальных датасета, каждый из своей выгрузки в `result/temp/request_results/`:

| Финальный датасет | Выгрузка запроса |
|---|---|
| `result/dataset.xlsx` | `request.xlsx` |
| `result/main.xlsx` | `request_main.xlsx` |

Если выгрузки нет, датасет пропускается, скрипт пишет, какого файла не хватает. Если нет ни одной выгрузки, скрипт завершается с ошибкой. Для каждой выгрузки скрипт читает лист `Result`, сверяет колонки с финальным датасетом, проверяет дубли `ticket_id` (только сообщает, не исправляет), ограничивает выбросы и сохраняет датасет. Файлы перезаписываются при каждом запуске.

### `scripts/outliers.py`

Правило ограничения сильных выбросов, используется в `finalize_dataset.py`. Для `gross`, `mail_sum` и `dispute_sum` значения тикетов с событием сортируются по убыванию. Выбросы — значения с самого верха, пока каждое больше следующего в 2 раза и больше (константа `GAP`). Они заменяются первым значением после них. `net` ограничивается по модулю с сохранением знака по выбросам `gross`, `gross = abs(net)`. Флаги, нули и `null` не меняются, поэтому ER и медианы остаются прежними.

## Логика запроса

Запрос берёт из sandbox-таблицы `ticket_id :: int`, `state_date :: date`, `log`, `com` (CTE `input_data`, единственное место со ссылкой на sandbox-таблицу). `log` и `com` проходят в выход без изменений. `state_date` задаёт окно тикета и дату курса, в группировке не участвует.

Все действия считаются только для сотрудника `5863` (`modified_by_id` / `created_by_id`). Окно тикета: от `window_start` (понедельник недели `state_date`) до `window_end` включительно. N в имени файла означает неделю `state_date` плюс N следующих недель:

| Файл | `window_end` | Дней в окне |
|---|---|---|
| `rvi_1w.sql` | `window_start + 13` | 14 |
| `rvi_3w.sql` | `window_start + 27` | 28 |
| `rvi_5w.sql` | `window_start + 41` | 42 |

Версии отличаются только `window_end` в CTE `input_data`. Логику правь в `rvi_1w.sql`, остальные два файла пересобирай из него заменой одного числа.

Блоки расчёта:

1. **Платежи** (`crm.tickets_payment_history`, без типов `Loyalty compensations - points` и `Loyalty compensation - promo`). Для каждого платежа берутся последняя версия сотрудника в окне и последняя версия другого пользователя до неё. Разница `paid_sum` и `received_sum` в рублях (неактивный платёж = 0) даёт дельту, `received` идёт с обратным знаком.
2. **Диспуты** (`crm.disputes_dispute_history`). Последняя версия сотрудника в окне со статусом `Refunded` и `is_active`, сумма с минусом.
3. **`net`** = дельты платежей + диспуты, в USD через `analytics.currency_converter.usd_in_rub` на дату `state_date`. **`gross`** = `abs(net)`.
4. **Письма** (`crm.mail_mail_history` + `crm.mail_ticketrelation`). Письма сотрудника в окне с темой `Сверка, не оплачивать` или `Reconciliation`. `mail_sum` = `amount_sell` тикета, если письмо было. `amount_sell` берётся из `public.booking` через `crm.tickets_ticket.order_item_id`.
5. **Флаг диспута на платеже.** Для каждого `payment_id` берётся последняя версия сотрудника в окне. Платёж засчитывается, если в ней `is_dispute = true` и `is_active = true`, а в окне было хотя бы одно включение флага сотрудником (переход из false/null в true). Сумма берётся из этой последней версии. Так платёж не задваивается, если флаг ставили дважды, и не засчитывается, если флаг поставили и потом сняли. `is_dispute` на тикет равен 1, если есть хотя бы один такой платёж, `dispute_sum` = сумма этих платежей в USD.

`paid_sum` и `received_sum` оборачиваются в `coalesce(..., 0)`. Иначе `null` в активной версии обнуляет дельту, и платёж молча выпадает из суммы.

Проверено пользователем, менять не нужно:
- `item_id` уникален в `public.booking`;
- в `analytics.currency_converter` одна строка на дату. Если курса на дату нет, тикет получит `net` = 0, это проблема данных, логика запроса это не обрабатывает;
- джойн на `max(modified_dt)` в блоке платежей не задваивает строки, потому что `modified_dt` хранится как `timestamp`;
- диспуты `Refunded` берутся целиком, без дельты к предыдущей версии. Сотрудник обычно создаёт диспуты с нуля, а не правит суммы в существующих.
