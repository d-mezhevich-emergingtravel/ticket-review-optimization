# Датасет 2026, недели 33–37

Из сырых Excel-выгрузок собираются два датасета для запроса: `dataset_for_request.csv` из всех файлов и `dataset_for_request_main.csv` только из `main/`. В каждом одна строка на тикет с полями `ticket_id`, `state_date`, `log`, `com`, `db_type`. Каждый файл загружается в две sandbox-таблицы, global и ru, и к каждой применяется своя версия запроса, всего четыре запроса. Выгрузки global и ru склеиваются в финальные датасеты `result/dataset.xlsx` и `result/main.xlsx`, при этом ограничиваются сильные выбросы в суммах.

Структура папки:

| Папка | Что внутри |
|---|---|
| `raw/` | сырые выгрузки в папках `main/`, `closed/`, `zero_losses/` |
| `scripts/` | `check_fields.py`, `prepare_dataset.py`, `merge_results.py`, `outliers.py` |
| `queries/global/`, `queries/ru/` | `rvi_1w.sql`, `rvi_3w.sql`, `rvi_5w.sql` для каждого контура |
| `result/` | `dataset.xlsx` и `main.xlsx` (финальные датасеты, собирает скрипт) |
| `result/temp/datasets_for_request/` | `dataset_for_request.csv` и `dataset_for_request_main.csv` (собирает скрипт) |
| `result/temp/request_results/` | `request_global.xlsx`, `request_ru.xlsx`, `request_main_global.xlsx`, `request_main_ru.xlsx` (выгрузки запросов) |

## Порядок работы

1. Положить Excel-файлы в `raw/`. Скрипты читают все `.xlsx` рекурсивно, временные файлы `~$…` пропускаются. Данные читаются с листа `Result`. Для основного датасета раскладка по подпапкам не важна, датасет main собирается только из файлов в `raw/main/`.

2. Проверить поля (необязательно, `prepare_dataset.py` делает ту же проверку):

   ```
   python3 scripts/check_fields.py
   ```

3. Собрать датасеты для запроса:

   ```
   python3 scripts/prepare_dataset.py
   ```

   Если какой-то файл не прошёл проверку или в `ticket_link` попался неизвестный домен, скрипт пишет, что не так, и останавливается, не трогая старые датасеты в `result/temp/datasets_for_request/`.

4. Каждый датасет из `result/temp/datasets_for_request/` загрузить в sandbox-таблицы обоих контуров: `analytics_sandbox` для global и `ru_analytics_sandbox` для ru. Подставить имена таблиц вместо `__` в выбранную версию запроса в `queries/global/` и `queries/ru/`. Версия окна должна быть одна и та же во всех четырёх запросах.

5. Выполнить запросы и выгрузить результаты в `result/temp/request_results/`:

   | Датасет для запроса | global | ru |
   |---|---|---|
   | `dataset_for_request.csv` | `request_global.xlsx` | `request_ru.xlsx` |
   | `dataset_for_request_main.csv` | `request_main_global.xlsx` | `request_main_ru.xlsx` |

6. Собрать финальные датасеты:

   ```
   python3 scripts/merge_results.py
   ```

Команды написаны для запуска из этой папки (`2026_w33-37/`). Пути строятся от папки периода, поэтому скрипты можно запускать из любой директории, указав полный путь к скрипту.

## Команды

| Задача | Команда |
|---|---|
| Проверить поля сырых выгрузок | `python3 scripts/check_fields.py` |
| Собрать датасеты для запроса | `python3 scripts/prepare_dataset.py` |
| Собрать финальные датасеты из выгрузок запросов | `python3 scripts/merge_results.py` |
| Проверить или собрать из другой папки с сырыми данными | добавить путь аргументом: `python3 scripts/prepare_dataset.py "путь/к/папке"` |

## Скрипты

### `scripts/check_fields.py`

На листе `Result` каждого файла проверяет:

- `ticket_id`, `state_date`, `ticket_link`: колонки есть и заполнены во всех строках (строка из пробелов считается пустой);
- `log` и `com`: колонки есть, пустые значения допустимы. Вместо `com` подходит `comm`.

Выводит результат по каждому файлу. Код выхода 1, если хоть один файл не прошёл.

### `scripts/prepare_dataset.py`

1. **Проверка** той же функцией, что в `check_fields.py`. Если хоть один файл не прошёл, сборка не запускается.
2. **Сборка.** Со всех файлов берутся `ticket_id`, `state_date`, `log`, `com` (`comm` переименовывается в `com`), строки не фильтруются. По `ticket_link` добавляется `db_type`:

   | Ссылка начинается с | `db_type` |
   |---|---|
   | `https://crm.ostrovok.in/` | `ru` |
   | `https://crm.etg.team/` | `global` |

   Ссылка с другим доменом останавливает сборку.
3. **Дубли `ticket_id`.** Остаётся строка с заполненным `log`. Если `log` заполнен у всех или ни у кого, остаётся строка с более ранним `state_date`.

Собираются два датасета с одинаковыми колонками:

| Файл | Из каких строк |
|---|---|
| `dataset_for_request.csv` | все файлы |
| `dataset_for_request_main.csv` | только файлы из `main/` (первый уровень внутри `raw/`) |

Оба файла сохраняются в `result/temp/datasets_for_request/`, формат: CSV с разделителем `;`, кодировка UTF-8, первая строка — заголовки, `state_date` в формате `YYYY-MM-DD`.

Дубли в каждом разбираются отдельно. Поэтому у тикета, который есть и в `main/`, и в другой папке, `state_date` и `log` в двух датасетах могут отличаться: в основной может попасть строка из другой папки.

### `scripts/merge_results.py`

Собирает два финальных датасета, каждый из своей пары выгрузок в `result/temp/request_results/`:

| Финальный датасет | global | ru |
|---|---|---|
| `result/dataset.xlsx` | `request_global.xlsx` | `request_ru.xlsx` |
| `result/main.xlsx` | `request_main_global.xlsx` | `request_main_ru.xlsx` |

Для каждого датасета:

1. Если нет хотя бы одной выгрузки из пары, датасет пропускается, скрипт пишет, каких файлов не хватает. Так в финал не попадает только один контур. Если не собрать ни один датасет, скрипт завершается с ошибкой.
2. Читает лист `Result` из обеих выгрузок. Колонки должны совпадать с колонками финального датасета, включая порядок, иначе скрипт останавливается.
3. Склеивает строки и проверяет дубли `ticket_id`: печатает, сколько их, в каких файлах и примеры. Дубли не исправляются.
4. Ограничивает выбросы (`outliers.py`) и сохраняет датасет (лист `Result`). Файл перезаписывается при каждом запуске.

### `scripts/outliers.py`

Правило ограничения сильных выбросов, используется в `merge_results.py`. Для `gross`, `mail_sum` и `dispute_sum` значения тикетов с событием (не `null` и больше 0) сортируются по убыванию. Выбросы — значения с самого верха, пока каждое больше следующего в 2 раза и больше (константа `GAP`). Они заменяются первым значением после них. Если самое большое значение не оторвано от следующего, сумма не меняется.

- `net` ограничивается по модулю с сохранением знака по выбросам `gross`, `gross = abs(net)`;
- `mail_sum` и `dispute_sum` ограничиваются каждая по своим выбросам;
- флаги, нули и `null` не меняются, поэтому ER и медианы остаются прежними.

Скрипт печатает верх каждого распределения с границей и множителем к следующему значению, чтобы было видно, что обрезано.

## Запросы

Логика запросов взята из периода 2025 без изменений. Отличаются только контуры и окна.

Все действия считаются для сотрудника `5863`. Окно тикета: от понедельника недели `state_date` до `window_end` включительно:

| Файл | `window_end` | Дней в окне |
|---|---|---|
| `rvi_1w.sql` | `window_start + 13` | 14 |
| `rvi_3w.sql` | `window_start + 27` | 28 |
| `rvi_5w.sql` | `window_start + 41` | 42 |

Внутри контура версии отличаются только `window_end`. Контуры отличаются фильтром и схемами:

| | global | ru |
|---|---|---|
| sandbox-таблица | `analytics_sandbox.__` | `ru_analytics_sandbox.__` |
| фильтр в `input_data` | `sb.db_type = 'global'` | `sb.db_type = 'ru'` |
| CRM | `crm.*` | `ru_crm.*` |
| booking | `public.booking` | `ru_public.booking` |
| курс USD | `analytics.currency_converter` | `ru_analytics.currency_converter` |

Логику правь в `queries/global/rvi_1w.sql`. Остальные версии global пересобирай из него заменой числа в `window_end`, ru-версии — заменой фильтра и схем по таблице выше.
