# 🛠 Сопровождение запроса основной выгрузки

Документ для тех, кто правит SQL основной выгрузки. Как выгрузкой пользоваться, описано в [основной выгрузке](unloads/main.md).

Владелец запроса: d.mezhevich.

---

## 📁 Две версии запроса

| Файл | Для чего |
|---|---|
| [`sql/main_prod.sql`](../../sql/main_prod.sql) | Рабочая версия. Её запускает специалист, она же сохранена в SQL Editor (query_id 9295816) |
| [`sql/main_dev.sql`](../../sql/main_dev.sql) | Отладочная версия с той же логикой. Ветки «проверка не нужна» в ней возвращают вердикт `Not check \| ...`, а незакрытые тикеты помечаются `Тикет не закрыт`. По ним видно, какая ветка сработала |

Любое изменение логики вносится в оба файла. После правки в репозитории нужно обновить и сохранённый запрос в SQL Editor.

## 🔗 Как устроен запрос

Запрос — цепочка CTE:

1. `thresholds` — допуски: превышение возврата над стоимостью при бесплатной отмене, допуски ORA с маржой и без. Допуски меняются только здесь.
2. `payment_summary` → `closed_tickets` → `input_data` — отбор закрытых тикетов с движением денег или ORA, `payout` и `refund` в USD, тип бронирования и сегмент.
3. Промежуточные CTE считают признаки тикета: платежи в рублях по курсу на дату создания заказа, ORA, виновника ошибки (с уточнением по Bug report и Mismatch report), отметку «диспут невозможен», тикеты modification, письма на сверку, диспуты.
4. `markers` собирает признаки в флаги и суммы, `ora_range_check` один раз считает попадание в допуск ORA.
5. `markers_with_check` — дерево `case`, которое ставит код `check`.
6. Финальный `select` добавляет `losses`, бизнес-юнит, владельца, команду, регион и ссылку на CRM.

## 🌳 Правила правки дерева `check`

- Условия `when` проверяются по порядку, срабатывает первое. Поэтому порядок важен: часть проверок ORA и платежей специально стоит до ветки, которая отключает проверки ORA для `i2r`, `r2i` и GGA.
- Ветка «проверка не нужна» в prod записывается как `then null -- <код>`, в dev — как `then 'Not check | ...'`. Такие ветки нельзя удалять: они останавливают перебор, иначе тикет попадёт в следующие проверки и получит лишний алерт.
- Номера null-веток (1.4, 1.11, 1.24, 2.8, 2.15) в prod пропущены, чтобы коды в prod и dev совпадали.
- При добавлении или переносе ветки обновите блок «ЛЕГЕНДА кодов check» в начале `markers_with_check` в обоих файлах и таблицу кодов в [описании выгрузки](unloads/main.md#-коды-check).
- Комментарии в SQL пишутся по-русски, ключевые слова — в нижнем регистре, группы веток разделяются строкой `-- ============ ... ============`.

## ⚠️ Известные ограничения

- **`:disable_check_ora`.** После деконсолидации компании нужный параметр ORA для `i2r`, `r2i` и GGA не работает в CRM, поэтому запрос всегда запускают с `'true'`, и эти проверки отключены. Когда можно будет вернуть `'false'`, пока неизвестно.
- **Контур письма на сверку (правило 2.3).** Письмо направляется в том контуре, где бронирование куплено у отеля. Сейчас правило проверяет только отели контура `global` (условие `m.type_country = 'global'`). Чтобы проверять письма в контуре `ru`, это условие в запросе нужно заменить на `m.type_country = 'ru'`.
